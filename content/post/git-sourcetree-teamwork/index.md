# 一、基本介绍
Git 是一款**分布式版本控制系统**，用来记录文件修改历史、多人协作、回溯代码。
他不仅可以多人使用，个人开发也可以使用这种模式。

### 核心作用
- 记录代码 / 文档每一次改动，随时**回退版本**
- 多人同时开发，自动合并代码
- 本地就有完整历史，不依赖中央服务器

### 基本概念
- **仓库（Repository）**：存放项目和版本历史的文件夹
- **提交（Commit）**：一次保存快照，带有说明和唯一标识
- **分支（Branch）**：独立开发线，不影响主版本
- **远程（Remote）**：云端仓库（如 GitHub、Gitee）

简单理解它就是一种云端存储的管理系统，你可以随时的存储和获取，类比于游戏中的话就是<strong>“存档”、“读档”、“回档”</strong>

### 重要性
- **商业地位：软件开发的“唯一标准”**：无论国内外的科技巨头还是初创公司，无论前端、后端还是游戏开发，Git 都是代码管理的默认方式。
- **岗位要求：从“要求”变成了“默认”**：就像岗位要求不会写“会使用操作系统”一样。它已和 Word、PPT 一样，是默认具备的基本素养。

## 3.介绍Git核心功能
<img src="media/862d26377544/Git%E6%A0%B8%E5%BF%83%E5%8A%9F%E8%83%BD.png" alt="Git核心功能" width="520" loading="lazy">
你可以先把 Git 理解为本地的东西——提交、建分支、合并，都是在你自己电脑上完成的，不需要联网。后面的拉取、推送、获取，才是和远端打交道。

更多使用方法请参照[Git官方手册](<https://git-scm.com/book/zh/v2>)

### 3.1提交（Commit）
将已暂存的更改保存到本地仓库，生成一个永久快照。在 Sourcetree 中勾选文件、填写提交信息后点击即可。每次开发项目之后，必须要提交那些应该暂存的文件，才能够切换分支。

### 3.2拉取（Pull）
从远程仓库下载最新代码，并自动合并到当前分支。相当于“获取 + 合并”的组合操作，保持本地与远程同步。
**日常 Pull 通常用于更新当前分支对应的远程分支。需要同步 main 时，可以先更新本地 main，再切换回功能分支并执行 Merge。不要随意将其他功能分支合并到自己的分支，确实需要时应先与队友沟通。**
就比如你微信更新，从网上直接下载并更新。
![获取形象图_005](<media/ad8e612f9ef8/%E8%8E%B7%E5%8F%96%E5%BD%A2%E8%B1%A1%E5%9B%BE_005.png>)

### 3.3推送（Push）
把本地已提交的记录上传到远程仓库，让团队成员能看到你的更改，或者拿到你的更改。
有点类似于你手机上的“检查系统更新”

### 3.4获取（Fetch）
仅从远程下载最新分支和提交信息，不会自动合并或修改你当前的工作。适合先查看远程更新，再决定如何合并。
就比如你去微信那里“检查更新”，检查完后会只会提示你要不要下载，并不会下载更新。![获取形象图_004](<media/3a8dd75468e0/%E8%8E%B7%E5%8F%96%E5%BD%A2%E8%B1%A1%E5%9B%BE_004.png>)

**每次开发项目前一定要按一次“获取”按钮，看看队友开发了什么。因为Sourcetree上不会时刻更新开发记录，需要手动获取。**
<img src="media/60560784b1db/%E8%8E%B7%E5%8F%96%E5%BD%A2%E8%B1%A1%E5%9B%BE_003.png" alt="获取形象图_003" width="697" loading="lazy">

### 3.5分支（Branch）
基于当前版本创建独立开发线，便于在不影响主线的情况下开发功能或修复缺陷。
![分支示例图_001](<media/d5b093c3207b/%E5%88%86%E6%94%AF%E7%A4%BA%E4%BE%8B%E5%9B%BE_001.png>)

### 3.6合并（Merge）
将某个分支的修改整合到当前分支，生成一个合并提交，统一两条不同的开发历史。![合并_001](<media/6b9ad88983da/%E5%90%88%E5%B9%B6_001.png>)

### 2.5 功能分支同步主分支

假设成员 A 正在 `feature/UI` 开发，成员 B 已将人物系统合并到 `main`。
成员 A 可以在 Sourcetree 中：
1. 先提交或妥善保存当前工作区改动。
2. 切换到本地 `main`。
3. Pull 远程 `main`，确保本地 main 最新。
4. 切换回 `feature/UI`。
5. 使用 Merge 功能选择 `main`，将其合并进当前 UI 分支。
6. 若有冲突，处理后在 Unity 内测试，再继续开发。
这一步不需要每天执行，只要 main 有重要更新、需要其他队员的新功能，或者准备将自己的功能合并到 main 时执行即可。

### 2.6 协作方案

**原方案：长期功能分支 + 开发后期集中合并**
团队成员从 `main` 创建各自的功能分支（如 `feature/UI`、`feature/Player`、`feature/Map`），独立开发，直到项目完成约 80%～90% 后，才集中合并回 `main`。

**存在的问题：**
1. **分支长期不更新：** 各成员的分支与 `main` 差异越来越大，最后集中合并容易产生大量冲突。
2. **集成测试过晚：** 各功能独立开发时正常，合并后可能出现接口不兼容、资源引用错误等问题。
3. **Unity 资源冲突：** 多人修改同一个 Scene、Prefab 或公共脚本时，容易产生难以解决的冲突。
4. **仓库上传缓慢：** 大量资源集中上传，叠加网络、仓库体积等因素，影响协作效率。
![Pasted image 20261016012400](<media/cff95b7176a8/Pasted%20image%2020261016012400.png>)

**新方案：功能分支开发 + 高频 Commit/Push + 按需同步 Main + 阶段性 Merge**
继续保留功能分支模式，但不再等到项目快完成才合并，也不把分支拆得过细。
**具体规范：**
1. **Branch：** 每人从最新 `main` 创建对应功能分支，一个相对完整的功能模块对应一个分支。
2. **Commit / Push：** 完成有意义的小进度后及时提交并推送到自己的功能分支，填写清晰的提交说明。
3. **同步 Main：** 当主分支有重要更新，或需要其他成员的新功能时，把最新 `main` 合并到自己的功能分支。
4. **Merge：** 功能达到可运行、可验收的稳定阶段后，由队长检查并合并到 `main`，不必等整个项目开发完成。
5. **资源管理：** 明确 Scene、Prefab 等资源的负责人，避免多人同时修改同一文件；合理配置 `.gitignore` 和 Git LFS。

## 3.冲突解决
一般项目开发中，需要反复合并队友或者自己开发的功能分支到main分支中，就容易发生冲突。

**常见的冲突情况:**
- **同一位置，不同内容**： 两个分支修改了同一个文件的同一行（或相邻行），比如一个分支改成 `A`，另一个分支改成 `B`，Git 无法判断保留哪个。
- **一方修改，一方删除**：分支 A 修改了某段代码，分支 B 删除了这段代码。Git 不知道是要保留修改还是执行删除，产生冲突。
- **文件重命名/移动冲突**：分支 A 重命名了文件，分支 B 也重命名了同一文件，或一个分支重命名、另一个分支修改内容，可能导致树冲突。
- **二进制文件冲突**：Git 无法逐行合并二进制文件（如图片、资源包等），只要两个分支都修改了同一个二进制文件，就会直接冲突，必须手动选择版本。
- **空白字符/空行导致的“伪冲突”**：即使代码逻辑完全相同，但如果两个分支在不完全相同的“上下文行”附近做了修改，或者修改区域的相邻空白行不同，Git 依旧可能判定为冲突。

这里举例"**同一位置，不同内容**"的冲突解决：
开发UI的队友新增了一个红色图片，并将代码输出从之前的“这是主菜单”，改为了“Hello World!”
<img src="media/40e7b8c81e82/%E4%BF%AE%E6%94%B9%E6%B5%8B%E8%AF%95_001.png" alt="修改测试_001" width="697" loading="lazy">

后续合并的时候，Sourcetree就会提示冲突。
![冲突解决_001](<media/93821312bf2a/%E5%86%B2%E7%AA%81%E8%A7%A3%E5%86%B3_001.png>)

这里会显示3种冲突的解决方式，使用“**我的版本(当前分支)**”和“**他人版本(合并的分支)**”解决冲突为**一边倒的快速解决**的冲突方式，而“**标记为已解决/未解决**”是**手动解决冲突**才用到的。
一般来说，如果队友开发的UI功能是完全由他开发并验证没问题，而且只是再旧版本的基础上修改完善就直接使用“他人版本”来解决就可以了。
![冲突解决_002](<media/7ce288d0e9d7/%E5%86%B2%E7%AA%81%E8%A7%A3%E5%86%B3_002.png>)

手动解决冲突：
git会帮你把冲突的地方标记出来
**<<<<< HEAD** 
**xxxxx   这里面的部分就是你当前分支(main)的内容**
**===== 冲突分隔符**
**xxxxx    这里面的部分就是你拉取分支(feature/UI)的内容**
**>>>>>feature/UI**

然后根据需求，采用“**当前的更改**”、“**传入的更改**”还是“**保留双方**”，修改完后回到sourcetree**标记为已解决**就行了

## 4.回溯版本
开发中，比如用AI写代码过猛，不仅bug没修好，还多了一堆bug，怎么办？一个个手动修改或者再让AI调不知道弄到猴年马月。要是能像游戏一样，回档回到上一个存档点就好了。
用git版本管理就不怕担心这个问题，它自带了版本回溯功能，可以一下“**回到解放前**”，完全不怕这些问题。无论是你开发功能时候想回退，还是main分支上想回退，都可以，操作都是一样的。

**请注意：任何重置前，确认工作区干净（已全部提交），否则未提交内容会丢失。**

选择分支，重置记录
![版本回溯_001](<media/810c4896edb8/%E7%89%88%E6%9C%AC%E5%9B%9E%E6%BA%AF_001.png>)

选择重置的方式：
- **强行合并（hard）—— 丢弃所有改动过的工作副本**
	- **工作目录**：**彻底清空**，所有未提交的改动（包括已暂存和未暂存）全部丢失，文件恢复为目标提交时的状态
	- **使用场景**：确定当前所有更改都不需要了，想彻底回到上一个干净版本。
- **混合合并（mixed）—— 保持工作副本并重置索引**
	- **工作目录**：**保留所有文件改动**，但这些改动变成“未暂存”状态
	- **使用场景**：想撤销 commit，但保留代码改动，以便重新整理后重新提交。
- **软合并（soft）—— 保持所有本地改动**
	- **工作目录**：**不变**
	- **使用场景**： 单纯撤销 commit 记录，但保留所有更改在暂存状态，方便直接重新提交（比如改一下 commit message）。
（PS：工作目录就是History里面那些很多条的信息记录）

# 五、结语
Git+Sourcetree这样的协作开发模式提升很大的效率和便利性，但是这有一个根本性前提：在开发之前、开发中，组长要提前规划好项目的开发大纲，谁负责什么部分，避免造成项目混乱和功能冗余。成员之间也要及时沟通开发进度，这样才能尽可能的在解决冲突上减少时间。
